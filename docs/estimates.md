# Оцінки shuffle до запуску (згенеровано scripts/estimate.py)

## Вхідні величини (scripts/explore.py, DuckDB, окремо від Spark)

* Файлів: 6, рядків: 20,332,093, байтів CSV: 2,194,482,008 (2,092.8 MiB).
* Прийнято після очищення: 19,674,794 поїздок.
* Ядер для local[*]: 8; maxSplitBytes = 134,217,728 Б => **17 map-задач** у stage A (формула Spark: min(128 MiB, max(4 MiB, (байти + файли*4 MiB) / ядра)), залишки файлів пакуються в спільні розділи). Межа 128 MiB діє для будь-якої кількості ядер ≤ 16, тож для такого ноутбука кількість map-задач від ядер не залежить.
* K1 = різних ключів (дата, PU, DO): 1,371,664; маршрутів (PU, DO): 43,673; у середньому 7,537 ключів на день.
* Денних рядків із n_trips >= 30: 182,292; маршрутів, що мають хоч один такий день: 1,889; маршрутів із >= 30 днями: 1,303.

## Як рахуємо записи shuffle

**Shuffle 1.** Часткова агрегація (HashAggregate partial = combiner) у кожній map-задачі залишає один запис на ключ, що зустрівся в цій задачі. Отже записів = Σ по map-задачах (різних ключів (дата, PU, DO) у задачі). Нижня межа - K1 (кожен ключ лише в одній задачі), верхня - min(прийнятих поїздок, K1 × 17). Модель (точна сума по розділах, зіставлених з байтовими межами шматків) дає **1,765,216** = 1.287 × K1.

**Shuffle 2.** Після shuffle 1 денні рядки маршруту лежать у розділах hash(дата, PU, DO) mod P. Кожен з P reduce-розділів дає по одному частковому підсумку на маршрут, що в ньому є. Для маршруту з d відібраними днями очікуємо P·(1 − (1 − 1/P)^d) таких розділів.

## Що очікуємо побачити у фактичному плані

* Job `analysis` (один `collect()`): stage A = Scan csv → Filter/Project → HashAggregate(partial) → Exchange hashpartitioning(trip_date, PU, DO, P); stage B = HashAggregate(final) → Filter(n_trips ≥ 30) → Project(avg_min) → HashAggregate(partial) → Exchange hashpartitioning(PU, DO, P); stage C = HashAggregate(final) → Filter(n_days ≥ 30) → Project(cv).
* Stage A: 17 задач; stage B і C: по P задач (P = spark.sql.shuffle.partitions, AQE вимкнено).
* Другий Exchange обов'язковий: розбиття hash(trip_date, PU, DO) не гарантує, що всі дні одного маршруту в одному розділі, тож вимогу ClusteredDistribution(PU, DO) воно не задовольняє.
* `spark.sql.shuffle.partitions` не змінює stage A (його задачі = розбиття CSV). Від P залежить кількість задач B і C та обсяг shuffle 2 (у ~P разів більше часткових підсумків на частий маршрут).
* Окремі job-и `quality` (звіт якості, свої маленькі shuffle) і `save-daily` у таблицю етапів не входять.
